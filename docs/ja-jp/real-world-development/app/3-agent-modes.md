プロジェクトに小さな機能を追加しました。より大規模な変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるため、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue を使って新機能を生成するところから始め、コードが有効で機能が期待どおりに動作することを確認し、最終的にプロジェクトにマージします。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使用します。通常は作業するファイルの種類ごとに異なるセッションやプルリクエスト (PR) を使いますが、ここでは中心となる概念に集中できるよう手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub Issue からエージェントの新しいセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズし、Model Context Protocol (MCP) による検証を追加して品質保証 (QA) エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者がカテゴリと発売元でゲームを絞り込めるようにする必要があります。バックログの Issue には機能が記載されていますが、カテゴリを組み合わせる方法など、実装前に合意が必要な詳細もあります。Plan モードで決定事項を整理し、Autopilot に範囲を明確にした実装を依頼します。

## 背景

人工知能 (AI) コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細が記載された Issue を開きます。
2. 構築する内容の計画を作成します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードのレビューと継続的インテグレーション (CI) が成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを基にしています。

この標準的な進め方に従うことで、AI が生成したコードが要件を満たし、手書きのコードと同じレビューを受けるようにできます。

## セッションモード

**セッションモード**は、エージェントに与える自律性の度合いを制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: 開発者とエージェントが協力して作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律的に作業し、入力を待たずにコードを書き、テストを実行して、タスクが完了するまで反復します。

Plan モードで開始し、計画をレビューしてから、Autopilot で実装します。

## Issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。既存の **Allow users to filter games by category and publisher** Issue を開きます。テンプレートに含まれる Issue のため、新しく作成する必要はありません。
2. **New session** を選択し、更新済みの `main` を基にした **new working tree** を選びます。

   ![GitHub Copilot app の Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。普段のターミナルでは実行できるのにセッションで見つからない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行します。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして持っています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を Issue の受け入れ条件と照らし合わせます。カテゴリと発売元による絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリの組み合わせや、一致するゲームがない場合の動作など、不明確な点を話し合います。

計画には、プロジェクトにすでにあるツールを使った lint、ユニットテスト、エンドツーエンド (E2E) テスト、型チェックを含めます。計画の範囲はフィルター機能の実装とテストに絞り、品質ワークフローを完了してから PR を作成します。計画は承認前に修正を依頼し、後で検証するために Issue の URL と合意事項を控えます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan** または使用中のバージョンで表示される同等のオプションを選びます。承認するとモードも切り替わると思い込まず、モード表示が **Autopilot** になっていることを確認します。

Copilot が計画に沿って実装を開始し、コードを生成してテストを実行しながら反復します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポートの競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、ほかのコードと同じようにマージ前にレビューします。コードを確認し、サイトを実行して動作も確かめます。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリと発売元の組み合わせも含め、結果を Issue と承認した追加の取り決めに照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、影響を受けたチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして配信し、ローカルサーバーを再利用することがあります。テスト対象が前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を試す

コードに問題がないように見えても、実際に動くか確認します。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリを選択して、結果がそのカテゴリに一致することを確認します。フィルターを解除してから、発売元を選び、結果がその発売元に一致することを確認します。
4. カテゴリと発売元のフィルターを組み合わせ、結果を Issue と承認済みの計画に照らし合わせます。複数カテゴリに対応する場合は、合意した組み合わせの動作を確認します。
5. 該当するゲームがない組み合わせも試して、空の状態を確認します。フィルターを解除またはリセットして、一覧全体が戻ることを確認します。
6. 確認が終わったら、次のプロンプトで、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンに向けてセッションを保持する

まだフィルター機能の PR を作成したり、マージしたりしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次は、フィルター機能のコードにカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 で作業をまとめた PR を作成してマージします。開発サーバーを停止した後はセッションをそのままにし、次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

- GitHub Issue からエージェントの新しいセッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザーキャンバスで機能を手動検証しました。
